# Fork maintenance (piomar123/immich)

<!-- cspell:ignore piomar rerere worktrees albumlink -->

This fork carries changes that aren't in an upstream Immich release (yet, or ever). They're kept as one branch each and combined into a generated branch, `patched`, which is what gets built into the server image that runs on `photos.piomar.me` (deployment: the `immich-ovh` repo).

| Branch | What it is | How it changes |
|---|---|---|
| `main` | exact copy of upstream `main` | fast-forward only (`gh repo sync piomar123/immich -b main`) |
| one branch per change, listed in `branches.txt` | the only copy of each change; most are the head of an upstream PR, so they're based on upstream `main` | rebased onto upstream `main` for upstream review |
| `fork-glue` (this branch, no upstream history) | `tools/fork/`: the branch list, the rebuild script, this README | rarely |
| `patched` (the fork's default branch) | generated by `rebuild.sh`, never edited by hand | rebuilt and force-pushed |
| `v<upstream>-piomar.<n>` tags | releases, what runs on the server (image `immich-server-piomar:<tag>`) | never moved |

Branches that aren't in `branches.txt` (mobile fixes, closed PR heads, `backup/*` tags) are not part of the build.

## Rebuild

```bash
tools/fork/rebuild.sh                                          # build on the latest release tag and test
tools/fork/rebuild.sh --image --push --tag v3.3.4-piomar.1     # and build the image and publish
```

The script resets `patched` (in the worktree `.worktrees/patched`) to the base, the latest upstream release tag unless `--base` says otherwise. Upstream releases are cut from `release/vX.Y` branches, which `main` doesn't contain, so a plain merge of a `main`-based branch would drag unreleased upstream commits into the build. Instead each branch's own commits (those not on upstream `main` and not on a branch listed above it, so a branch can be stacked on an earlier one) are cherry-picked onto `patched` (`-x`, so each one names its source) and merged with `--no-ff`; then `fork-glue` is merged. `git log --first-parent patched` shows one merge per branch.

Tests: `pnpm install`, the plugin SDK build, the server type check and the server unit tests (pnpm through `npx`, at the version upstream's `package.json` pins). The web app is only compiled by the image build.

`--image` builds `server/Dockerfile` for `linux/amd64` (the server's architecture; emulated on an arm64 Mac, which takes a while) and loads it into the local Docker as `immich-server-piomar:<tag>`. Ship it with `docker save immich-server-piomar:<tag> | gzip | ssh ovh 'gunzip | docker load'` and follow the deploy steps in `immich-ovh`'s `ARCHITECTURE.md`.

- **Conflicts** between branches are replayed by `git rerere` (enabled by the script; the resolutions live in this clone's `.git/rr-cache`). A new conflict stops the script: resolve it in `.worktrees/patched`, `git cherry-pick --continue`, and run the script again.

## When things change

- **A branch changes** (review fixes, a rebase): push the branch, rebuild.
- **Upstream merges a PR:** once it's in a release, delete its line from `branches.txt` on `fork-glue`, push, rebuild. Until then keep it: the release the build is based on doesn't have it.
- **A new change:** branch it off upstream `main`, push it, add a line to `branches.txt`, rebuild.
- **A new upstream release / a fork release:** rebuild with `--image --push --tag v<release>-piomar.<n>`, `<n>` starting at 1 for each upstream release. Check the release's migrations and `docker/docker-compose.yml` changes before deploying.

## Known combination

`feat/email-my-immich-links` (fork-only since upstream closed #32347) is stacked on `feat/email-album-thumbnail-link`: both change the album invite/update emails, and without a conflict git would leave the thumbnail's `<Link>` pointing at the plain album URL. Its last commit makes the thumbnail use `albumLink` (the my.immich.app link when that setting is on), like the button and the text link. Rebase it onto `feat/email-album-thumbnail-link` whenever that PR branch changes.
